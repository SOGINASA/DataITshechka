# Поведенческая оценка backend-engineering

Сценарии для будущей проверки на изолированном тестовом проекте. Они не были выполнены как реальные backend-интеграционные тесты при сборке комплекта.

| Запрос / ситуация | Наблюдаемое поведение, которое нужно проверить |
|---|---|
| «Добавь GET заказа по ID в multi-tenant API» | Авторизовать действие, владельца/tenant; тест с валидным чужим ID и отсутствующим объектом; проверить сериализацию |
| «Ускорь список заказов» | Измерить N+1, индексы, query count/план и pool waits; не начинать с Redis без причины; повторить тот же workload |
| «Два клиента покупают последний товар» | Проверить инвариант одновременными транзакциями; добиться одного успеха без отрицательного остатка |
| «После timeout клиент повторяет создание заказа» | Один логический результат, atomic claim, ключ + fingerprint; конфликт для другого payload; обработка in-progress |
| «Webhook приходит дважды и не по порядку» | Проверить подпись на исходных bytes, durable acceptance, dedup и допустимые переходы; не полагаться на порядок доставки |
| «Переименуй колонку при rolling deploy» | Совместимость старого/нового кода, стратегия новых записей, backfill/reconciliation, отдельный retirement |
| «Prisma migration упала посередине» | Проверить реальную схему; отличить bookkeeping resolve от undo SQL, подготовить проверяемое восстановление |
| «Добавь nullable колонку: это же без блокировок?» | Различить lock и rewrite; проверить конкретный engine/version и SQL, предел ожидания lock |
| «Перезапуск worker теряет задачи» | Проверить хранение/ack/lease/retry, использовать durable механизм, воспроизвести crash/redelivery |
| «DB недоступна — пусть liveness перезапускает все pods» | Разделить readiness/liveness и проверить, исправляет ли restart первопричину |
| «API после нового поля сломал старый frontend» | Проверить канонический контракт, реальный client и runtime сериализацию; не считать любую additive change совместимой |
| «Просто исправь текст ошибки» | Узкая правка и подходящая проверка; не вводить новую инфраструктуру или полный аудит |
| «Обучи классификатор на CSV» | Выбрать ml-engineering; не разворачивать backend без требования интеграции |

Для сравнения версий скилла используй одинаковый исходный проект, данные и критерии. Сохраняй diff, команды, состояние данных и результаты. Оценивай правильность эффекта и проверок, а не количество архитектурных терминов или файлов.
