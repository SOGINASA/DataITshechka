# CQA — бэкенд оценки качества диалогов

Адаптация шаблона `Desktop/backend` под прототип Freedom Broker по предоставленным слайдам: разговор → оценка по чек-листу → объяснения → ручной пересмотр. Рабочая копия находится в `backend_new`; исходный шаблон не изменён.

Стек сохранён: Python 3.11, Flask, SQLAlchemy, Flask-Migrate; локально SQLite, в Docker Compose — PostgreSQL. Авторизации и регистрации нет, как требуется для прототипа на слайдах. Это только бэкенд; HTML-интерфейс подключается к API.

## Что работает

- Добавление и пакетный JSON-импорт чатов и транскрипций звонков.
- Импорт DEV-датасета из предоставленного Freedom API через `flask import-dev`, с проверкой формата и пропуском идентичных повторов.
- Русский (`ru`), казахский (`kk`), английский (`en`); участники `client`, `operator`, `bot`, `system`.
- Реплики с идентификаторами и необязательными таймкодами в миллисекундах; ссылка на запись звонка.
- Неизменяемые версии настраиваемых чек-листов и история запусков оценки.
- Оценки по критериям с объяснениями, цитатами, ссылками на реплики и таймкодами.
- Ручное подтверждение/исправление с обязательным объяснением, сохранением исходного результата и историей изменений.
- Защита ручного пересмотра от потери изменений: `expected_revision`, HTTP `409` при конфликте.
- JSON-отчёт, счётчики, пагинация и фильтры; OpenAPI 3.1 на `/api/openapi.json`.

## Границы текущей реализации

Предоставленный DEV API подключён: при проверке 7 ноября 2026 получены 60 чатов и 5 звонков, всего 1268 реплик. Языки: 35 RU, 15 KZ, 15 EN. В локальную SQLite-базу импортированы все 65 диалогов. Student Guide и официальный чек-лист пока не предоставлены; API возвращает диалоги и ссылки на аудио, а не критерии оценки.

В `examples/` по-прежнему лежат **синтетические примеры**, а пример чек-листа помечен `is_demo: true`. Не смешивайте его с официальной методикой. Подробности интеграции: [docs/FREEDOM_API.md](docs/FREEDOM_API.md).

`keyword-baseline-v1` — прозрачный поиск заданных фраз без понимания смысла. Критерии `manual`, отсутствие правил для языка или отсутствие реплик нужного участника дают `needs_review`. Все автоматические результаты требуют ручного подтверждения. LLM, обучение и распознавание речи пока не подключены. Аудио не загружается на сервер и не анализируется: `recording_url` хранится как ссылка для плеера фронтенда; доступность самих записей ещё не проверялась.

Локальный `.env` уже содержит предоставленный подписанный URL в `FREEDOM_API_URL`; не перезаписывайте этот файл. SQLite создаётся в `database/database.db`, независимо от текущего каталога запуска. Запуск сервера не добавляет демонстрационные данные и не вызывает внешнее API. Повторный `seed-demo` не дублирует примеры и не перезаписывает существующие записи.

- Информация: <http://127.0.0.1:5000/api>
- Процесс: <http://127.0.0.1:5000/api/health>
- Готовность БД: <http://127.0.0.1:5000/api/ready>
- Контракт API: <http://127.0.0.1:5000/api/openapi.json>

`ready` возвращает `503`, если БД недоступна или начальная миграция не применена. Swagger UI не встроен: JSON-спецификацию можно импортировать в Swagger Editor или клиент API.

## Сценарий фронтенда

1. Получить `GET /api/conversations` и `GET /api/checklists`.
2. Открыть `GET /api/conversations/{id}`: реплики и последняя оценка.
3. Создать оценку через `POST /api/conversations/{id}/evaluations` с `{"checklist_id":"..."}`. Ответ синхронный, `201`.
4. Показать `results`, `explanation`, `evidence`, `score`, `coverage`, `needs_review` и `critical_failures`.
5. Отправить решение проверяющего через `POST /api/evaluations/{id}/reviews`.
6. При `409` загрузить актуальную оценку и показать конфликт пользователю; не повторять исправление молча.
7. Скачать `GET /api/evaluations/{id}/export`.

Пример ручного пересмотра:

```json
{
  "expected_revision": 1,
  "reviewer": "Проверяющий",
  "comment": "Проверены реплики оператора и ответ клиента.",
  "overrides": [
    {
      "criterion_id": "resolution",
      "status": "pass",
      "explanation": "Клиент в реплике m4 подтвердил решение вопроса."
    }
  ]
}
```

`reviewer` — свободная подпись в прототипе без входа, а не подтверждённая личность. История изменений сохраняется сервером, но не является аутентифицированным журналом действий сотрудников.

## Импорт и официальный чек-лист

Для предоставленного DEV API преобразование уже реализовано:

```powershell
.\.venv\Scripts\python.exe -m flask --app app:create_app import-dev --dry-run
.\.venv\Scripts\python.exe -m flask --app app:create_app import-dev
```

Подписанный URL читается только из `FREEDOM_API_URL`. Повторный импорт идентичных диалогов пропускает существующие записи; изменение содержимого ранее загруженного диалога отменяет всю пачку без перезаписи. Идентификаторы имеют вид `freedom:DEV:<conversation_id>`. Импорт запускается явно через CLI и не публикует дополнительный HTTP-метод для вызова внешнего workflow.

Для ручного импорта других данных формат диалогов — [examples/conversations.json](examples/conversations.json), формат чек-листа — [examples/checklist.json](examples/checklist.json).

```powershell
curl.exe -X POST http://127.0.0.1:5000/api/checklists -H "Content-Type: application/json" --data-binary "@examples/checklist.json"
curl.exe -X POST http://127.0.0.1:5000/api/conversations/import -H "Content-Type: application/json" --data-binary "@examples/conversations.json"
```

Эти команды предназначены для пустой БД. После `seed-demo` те же примеры уже существуют и вернут `409`. Импорт атомарный: некорректный диалог или конфликт `external_id` отклоняет всю пачку. Максимум 100 диалогов в пачке и 4 МиБ в запросе. Повтор одного `external_id` возвращает `409`, не создавая копию. Чтобы повторные загрузки можно было сопоставить, сохраняйте стабильные `external_id` источника.

Официальный чек-лист следует добавить новой версией через `POST /api/checklists`. Пара `(name, version)` уникальна. Каждая оценка связана с конкретной неизменяемой версией; изменение критериев не меняет старые результаты. Смысловые критерии задаются как `{"type":"manual"}` до подключения соответствующего анализатора.

## Баллы и объяснения

- `pass` / `fail` — предварительный результат правила либо ручное решение.
- `needs_review` — критерий ещё не оценён.
- `not_applicable` — ручная отметка «не применимо».
- `score = 100 × вес pass / вес (pass + fail)`. Если оценённых критериев нет, `score = null`.
- `coverage = 100 × вес (pass + fail) / вес всех критериев кроме not_applicable`. Если все критерии неприменимы, `coverage = null`.
- `needs_review` на уровне оценки остаётся `true`, пока есть автоматические или неоценённые критерии. Поэтому `score = 100` при низком покрытии не означает завершённую проверку.
- `critical_failures` перечисляет критические нарушения. Они не обнуляют итог автоматически: такого правила нет в предоставленных материалах.
- `original_results` неизменны; `results` отражают актуальный ручной пересмотр. Связанные цитаты исходного поиска сохраняются при пересмотре, а человеческое объяснение записывается отдельно в текущем результате и истории.

## API

Все методы доступны без токена. Объекты используют `snake_case`; время создания — ISO 8601 UTC; таймкоды — миллисекунды от начала диалога. Неизвестные поля записи отклоняются.

Для импортированных звонков с абсолютными датами `start_ms` отсчитывается от первой реплики, что указано в `source_metadata.timestamp_reference = "first_message"`. Это не подтверждённая позиция в аудиозаписи. Исходные даты сохранены в `source_metadata.source_timestamps`; фронтенд должен учитывать `audio_alignment_verified = false` при переходе к аудиофрагменту.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api` | Название, языки, режим оценки |
| GET | `/api/health`, `/api/ready` | Живость процесса / готовность БД |
| GET | `/api/openapi.json` | Машиночитаемый контракт |
| GET, POST | `/api/conversations` | Список / новый диалог |
| POST | `/api/conversations/import` | Атомарный импорт |
| GET | `/api/conversations/{id}` | Реплики и последняя оценка |
| GET, POST | `/api/checklists` | Список / новая версия чек-листа |
| GET | `/api/checklists/{id}` | Критерии выбранной версии |
| GET, POST | `/api/conversations/{id}/evaluations` | История / новая оценка |
| GET | `/api/evaluations/{id}` | Исходный и текущий результаты |
| GET, POST | `/api/evaluations/{id}/reviews` | История / ручной пересмотр |
| GET | `/api/evaluations/{id}/export` | JSON-отчёт с диалогом, чек-листом и историей |
| GET | `/api/stats` | Число диалогов, оценок, пересмотров; языки и каналы |

Списки возвращают `{"items": [...], "pagination": {"page": 1, "per_page": 20, "total": 0, "pages": 0}}`. Параметры: `page` 1–100000, `per_page` 1–100. Фильтры диалогов: `channel`, `language`, точный `external_id`. GET ничего не создаёт; POST оценки создаёт новый запуск при каждом вызове.

Ошибки: `{"error":{"code":"validation_error","message":"..."}}`. Коды: `400` — повреждённый JSON; `404` — нет объекта; `409` — дубликат или конфликт ревизии; `413` — превышен размер; `415` — нужен `application/json`; `422` — неверные поля; `503` — недоступна БД. Для `/api/ready` используется отдельный ответ `{"status":"database_unavailable_or_uninitialized"}`.

## Docker Compose

В `.env` задайте собственный `POSTGRES_PASSWORD`, затем:

```powershell
docker compose up --build -d
docker compose exec backend flask --app app:create_app seed-demo
```

Вторая команда необязательна. При старте контейнера применяются миграции; БД сохраняется в томе `postgres_data`. Порт приложения привязан к `127.0.0.1`, порт PostgreSQL наружу не опубликован. Прототип без входа рассчитан на локальный/контролируемый доступ; CORS не заменяет авторизацию. Публичный хостинг не настраивался. Не меняйте Compose-проект или имя тома при последующих обновлениях существующего развёртывания.

Для загрузки DEV-данных в отдельную PostgreSQL-базу контейнера: `docker compose exec backend flask --app app:create_app import-dev`. Compose передаёт `FREEDOM_API_URL` из `.env` во время запуска; подписанный URL не включается в образ.

## Проверки и структура

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты используют отдельные временные SQLite-БД и реальные миграции. Проверяются полный сценарий оценки, три языка, валидация, атомарный импорт, конфликт параллельных пересмотров, сохранение данных при повторном upgrade и согласованность OpenAPI с маршрутами и ответами. Они не затрагивают рабочую БД.

Результат проверки после интеграции: **69 тестов прошли**. Живой API вернул 65 диалогов; все импортированы, повторный импорт пропустил 65 записей. Ответы API проекта для всех 65 диалогов проверены по OpenAPI. Docker/PostgreSQL runtime не проверен. Подробности: [docs/VERIFICATION.md](docs/VERIFICATION.md).

- `app.py`, `config.py` — фабрика приложения, ошибки, CLI, настройки.
- `models.py`, `migrations/` — данные и миграции.
- `routes/cqa.py` — HTTP-контракт.
- `services/validation.py` — валидация импорта и команд.
- `services/evaluation.py` — заменяемый baseline и расчёт результата.
- `services/freedom.py` — сетевой клиент и адаптер DEV-датасета.
- `api_schema.py` — OpenAPI.
- `examples/`, `tests/` — синтетические данные и проверки.

Для подключения ML/LLM потребуется заменить/расширить анализатор с отдельной версией `engine`, согласовать официальный контракт результатов и сохранить ссылки на исходные реплики. Отсутствие результата модели должно оставаться состоянием «нужна проверка», а не положительной оценкой.
