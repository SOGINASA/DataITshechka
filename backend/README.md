# CQA — бэкенд оценки качества диалогов

Flask-бэкенд проекта `BimBomBam`, адаптированный под **Student Guide v3** и официальный **CQA Chat Quality Checklist** Freedom Broker. Поддерживает импорт транскриптов, настраиваемые чек-листы, оценку через локальный Ollama, объяснения, апелляции и решения проверяющего.

Python 3.11 · Flask · SQLAlchemy · Alembic/Flask-Migrate · SQLite локально / PostgreSQL в Compose. Прототип работает без регистрации и входа. Фронтенд находится в соседнем `../frontend`; его интерфейс и интеграция не входят в эту backend-проверку.

Подробное соответствие требованиям, формулы и ограничения: [docs/SPEC_ALIGNMENT.md](docs/SPEC_ALIGNMENT.md).

## Что уже подготовлено

- Официальный начальный чек-лист: 8 критериев, сумма весов 100, типы binary/scale/flag, шкалы 0–20 и 0–10, ограничения N/A и секции.
- Создание новых версий чек-листа. Изменённые критерии передаются модели через настройки, без правок кода.
- Прозрачный пересчёт: числовой балл относительно максимума шкалы, перераспределение при N/A, округление до двух знаков; грубые нарушения отдельно.
- Апелляция по критерию и отдельное решение проверяющего: подтвердить или изменить, с причиной и историей.
- Исходная оценка, спорный результат, текущий результат и история изменений; защита от одновременной перезаписи через `expected_revision`.
- Импорт DEV и контрольной группы, сохранение исходных таймкодов, ссылки на записи звонков.
- Проверяемый контракт Ollama: допустимые значения, полнота ответа и реальные ID реплик. Ошибка модели не превращается в положительную оценку.
- OpenAPI 3.1: `/api/openapi.json`.

### Загрузка экранов

Фронтенд использует `GET /api/workspace/overview`, `/api/workspace/conversations`, `/api/workspace/conversations/{conversation_id}` и `/api/workspace/appeals`. Полные параметры и ответы описаны в OpenAPI. Существующие API сохранены.

Обзор возвращает сводку по всей базе, максимум шесть диалогов и четыре краткие апелляции; транскрипты не выбираются из БД. Список диалогов поддерживает `page`, `per_page` (1–100), `search`, `language`, `channel`, `status`. Ответ содержит только текущую страницу. Карточка загружает один разговор, его историю оценок, решения и чек-листы пакетными SQL-запросами без запроса на каждый объект. Список апелляций загружает подробности только выбранного разговора.

Сводные баллы вычисляются на сервере по последней оценке каждого диалога; неполные оценки и N/A не заменяются нулём. При одинаковом времени запуска последняя оценка выбирается по ID. График охватывает последние семь дней в UTC+5. Обзор выполняет два SQL-запроса независимо от количества диалогов. Вычисление сводки и фильтрация по баллам пока линейны по числу последних оценок; при больших объёмах следующим шагом будет хранение вычисленных показателей с обновлением при оценке/пересмотре. HTTP-ответы уже ограничены размером экрана.

Сначала обновляется бэкенд, затем фронтенд. Изменение не требует миграции и не меняет данные или конфигурацию окружения. `tests/test_workspace.py` проверяет сводку, фильтры, пагинацию, количество SQL-запросов, отсутствие транскриптов и обновление после пересмотра.

В локальной SQLite уже есть 65 диалогов: **60 синтетических чатов и 5 реальных звонков** согласно Student Guide; RU 35 / KZ 15 / EN 15. Официальный чек-лист загружен. Модель Ollama ещё не выбрана и не установлена; смысловые результаты на реальных диалогах не получены.

## Ollama локально или на VPS

Укажите в `.env` адрес уже запущенного сервиса и точное имя уже загруженной модели:

```dotenv
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=<точное имя модели из ollama list>
OLLAMA_TIMEOUT=120
OLLAMA_NUM_CTX=32768
OLLAMA_NUM_PREDICT=4096
```

После изменения окружения перезапустите бэкенд. Для локальной RTX 4050 Laptop 6 ГБ подготовлен `scripts/local_model.ps1`: официальный portable runtime и `qwen3:4b`. Для VPS размер выбирается отдельно по RAM/VRAM. Качество RU/KZ/EN проверяется реальным прогоном, поддержка structured outputs не гарантирует правильность решений.

Для обычной оценки отправьте `POST /api/conversations/{id}/evaluations`:

```json
{"checklist_id": "<id официального чек-листа>"}
```

Режим `auto` выбирает Ollama, если в чек-листе есть критерии с `rule.type=semantic`. Можно явно передать `engine: "ollama"` или `engine: "baseline"`. В baseline смысловые критерии остаются `needs_review`; это полезно для ручного рабочего процесса, но не является автоматической смысловой оценкой. Без `OLLAMA_MODEL` официальный чек-лист в режиме auto возвращает 503, а не фиктивный успех.

В Ollama отправляются транскрипт и вся выбранная конфигурация критериев. Цитаты берутся сервером по ID сообщения; модель не задаёт общий балл. У ответа сохраняются модель, версия промпта, время, число вызовов и доступные счётчики токенов в `run_metadata`. Контекст не обрезается молча: консервативная проверка по UTF-8-размеру может потребовать увеличить `OLLAMA_NUM_CTX`; это увеличивает потребление памяти.

Команда `import-dev` сохранена как совместимый псевдоним. `--dry-run` получает данные и проверяет их, но не сохраняет. `--file database/dev-response.private.json` читает сохранённый ответ без сети. Подробности формата и сохранения дат: [docs/FREEDOM_API.md](docs/FREEDOM_API.md). Контрольный набор пока не запрашивался, поскольку его `group_id` ещё не предоставлен.

## Результаты и баллы

Каждый критерий возвращает тип, `value`, `status`, вес, `points`, `effective_weight`, `effective_points`, объяснение и доказательства. `evidence[].message_id` указывает на реплику; `reviewed_range` задаёт проверенный участок для пропущенного действия/отсутствия нарушения. `section` связывает критерий с результатом секции.

| Тип | Значение и статус |
|---|---|
| binary | `true` → `pass`, `false` → `fail` |
| scale | Число строго из настроенной шкалы, `status=scored` |
| flag | `true` → нарушение (`fail`), `false` → не выявлено (`pass`); вес 0 |
| N/A | `value=null`, `status=not_applicable`; только если `allow_na=true` и выполнено `na_condition` |
| Не оценено | `value=null`, `status=needs_review` |

Базовые баллы шкалы: `weight × value / max(scale)`. Итог: `100 × сумма баллов / сумма применимых весов`. N/A исключается из знаменателя. При отсутствии применимых весов итог null. Флаг грубой ошибки не обнуляет сумму и не входит в знаменатель.

`score` — оценка по уже оценённой части. Если остаются неоценённые критерии с весом, `score_is_partial=true`, `final_score=null`, а `coverage` показывает покрытие. Неизвестный флаг отображается как `gross_error_detected=null`, а не false. `needs_review=true` также указывает на неподтверждённые человеком выводы модели. `original_results` и `original_summary` сохраняют исходную оценку.

## Апелляция и решение

Сначала создайте обращение — оно не меняет балл:

```http
POST /api/evaluations/{id}/appeals
Content-Type: application/json
```

```json
{
  "criterion_id": "consultation",
  "expected_revision": 1,
  "author": "Оператор",
  "comment": "Прошу пересмотреть полноту консультации."
}
```

Затем отдельным действием проверяющего:

```http
POST /api/appeals/{id}/decision
Content-Type: application/json
```

```json
{
  "expected_revision": 1,
  "decision": "change",
  "reviewer": "Проверяющий",
  "reason": "Все существенные вопросы закрыты.",
  "override": {
    "criterion_id": "consultation",
    "value": 20,
    "explanation": "В ответе дан полный следующий шаг.",
    "evidence_message_ids": ["3"]
  }
}
```

ID реплики в примере условный: используйте реальный ID из выбранного диалога. Для подтверждения отправьте `decision: "confirm"` без `override`. `expected_revision` — текущая ревизия **оценки**, не апелляции. Повтор закрытия и устаревшая версия дают 409. Если спорный балл уже изменён другим проверяющим, подтвердить прежнее значение нельзя.

Прямой ручной пересмотр `/api/evaluations/{id}/reviews` тоже сохранён. Передавайте `overrides` с теми же значениями и доказательствами, плюс `expected_revision`, `reviewer`, `comment`. Подписи автора и проверяющего свободные: прототип не аутентифицирует личности.

## Изменение чек-листа

`POST /api/checklists/{id}/versions` принимает новую `version` и изменённые `criteria`, при необходимости `name`/`description`. Исходная версия и старые оценки остаются неизменными. Новый ID нужно выбрать при следующей оценке. Поля критерия: `id`, `title`, `description`, `weight`, `answer_type`, `allow_na`, `na_condition`, `scale`, `section`, `critical`, `require_evidence`, `rule`.

Начальная конфигурация: [checklists/freedom_chat_v1.json](checklists/freedom_chat_v1.json). Для смысловых критериев используйте `rule: {"type":"semantic"}`. Для шкалы задайте возрастающие ступени `{value,label}`, начиная с нуля. Для флага задайте вес 0. Разрешённый N/A требует явного условия.

## Основные API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api`, `/api/health`, `/api/ready`, `/api/openapi.json` | Информация, состояние, контракт |
| GET, POST | `/api/conversations` | Диалоги / загрузка одного диалога |
| POST | `/api/conversations/import` | Импорт до 100 диалогов в нормализованном формате |
| POST | `/api/datasets/import` | Загрузка набора организаторов по group_id |
| GET | `/api/conversations/{id}` | Транскрипт, источник, последняя оценка |
| GET, POST | `/api/checklists` | Версии / создание чек-листа |
| GET | `/api/checklists/{id}` | Настройки выбранной версии |
| POST | `/api/checklists/{id}/versions` | Сохранение изменений новой версией |
| GET, POST | `/api/conversations/{id}/evaluations` | История / запуск оценки |
| GET | `/api/evaluations/{id}` | Исходный и текущий результаты |
| GET, POST | `/api/evaluations/{id}/appeals` | Апелляции / новое обращение |
| GET | `/api/appeals/{id}` | Спорная оценка и статус |
| POST | `/api/appeals/{id}/decision` | Решение проверяющего |
| GET, POST | `/api/evaluations/{id}/reviews` | История / прямой пересмотр |
| GET | `/api/evaluations/{id}/export` | Отчёт с диалогом, чек-листом, апелляциями и решениями |
| GET | `/api/stats` | Счётчики, включая открытые апелляции |

Списки: `{items: [...], pagination: {page, per_page, total, pages}}`; `page` 1–100000, `per_page` 1–100. Фильтры диалогов: `channel`, `language`, `external_id`, `dataset_group_id`. Ошибки: `{error: {code, message}}`. Коды 400/415/422 — запрос; 404 — объект; 409 — конфликт; 413 — размер; 502 — некорректный ответ источника/модели; 503 — недоступный сервис/БД. Максимальный входящий JSON — 4 МиБ.

У звонков `start_ms` отсчитан от первой реплики, а не от подтверждённого начала аудио. Исходные даты сохранены, `audio_alignment_verified=false`. Аудио не скачивалось; плеер и точность переходов должны быть проверены на фронтенде. ASR не нужен: организаторы выдали транскрипты.

## Docker Compose

Настройка VPS, `.env`, PostgreSQL и автодеплоя только бэкенда: [deploy/README.md](deploy/README.md).

Задайте `POSTGRES_PASSWORD` в `.env`, затем `docker compose up --build -d`. Миграции и начальный официальный чек-лист применяются при старте контейнера. Данные хранятся в существующем томе `postgres_data`; локальная SQLite не переносится в PostgreSQL автоматически.

Для импорта: `docker compose exec backend flask --app app:create_app import-dataset --group DEV`.

Ollama в этом Compose не устанавливается. Если она работает на хосте, используйте в `.env` `OLLAMA_BASE_URL=http://host.docker.internal:11434`; маршрут host-gateway добавлен. Сервис должен быть доступен с контейнера: привязка Ollama только к loopback хоста этого не обеспечивает. Если Ollama в отдельном контейнере общей сети, задайте его внутреннее имя. Не публикуйте порт модели в интернет ради этого подключения.

Порт бэкенда по умолчанию привязан к 127.0.0.1. Не меняйте имя Compose-проекта и тома существующего развёртывания. Развёртывание и Docker/PostgreSQL runtime в этой среде не проверены.
