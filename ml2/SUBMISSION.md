# Сдача результатов CQA

Источник: неизменённое приложение организаторов в
`references/CQA_Student_Guide_Appendix_Results.pdf`, формат 1.0.

В корне репозитория должны появиться `results/dev/results.json` (60 чатов + 5 звонков)
и `results/prod/results.json` (10 контрольных чатов). На получение контроля,
обработку, проверку и push выделен один час. Команды ниже выполняются из корня проекта.
В `--team` укажите настоящее название команды.

## DEV

Оценить весь набор двумя запусками с подходящими чек-листами. Это длительный прогон;
не путать с уже выполненной проверкой трёх примеров.

```sh
python3 -m ml2 run --input ml2/data/dev.chats.jsonl --output ml2/runs/dev-chats-final
python3 -m ml2 run --input ml2/data/dev.calls.jsonl --rubric ml2/configs/voice.json --output ml2/runs/dev-calls-final
python3 -m ml2 submission --input ml2/data/dev.raw.json --runs ml2/runs/dev-chats-final ml2/runs/dev-calls-final --split dev --team 'НАЗВАНИЕ КОМАНДЫ' --output results/dev/results.json
python3 -m ml2 validate-submission --input ml2/data/dev.raw.json --submission results/dev/results.json --split dev
```

Добавьте одинаковые `--knowledge` и корректный `--as-of`, если получена официальная
база знаний. Сначала проверьте вместимость входа на небольшом development-наборе.
Экспорт не запускает модель и не смешивает дублирующиеся оценки одного диалога.
Если нужно заменить результат, выберите согласованные каталоги запусков без пересечений.

## Контроль

Способ получения организаторы ещё сообщат. Сохраните исходный ответ/массив
в `ml2/data/prod.raw.json`; исходные ID менять нельзя.

```sh
python3 -m ml2 normalize --input ml2/data/prod.raw.json --channel chat --output ml2/data/prod.chats.jsonl
python3 -m ml2 run --input ml2/data/prod.chats.jsonl --output ml2/runs/prod-final --purpose control
python3 -m ml2 submission --input ml2/data/prod.raw.json --runs ml2/runs/prod-final --split prod --team 'НАЗВАНИЕ КОМАНДЫ' --output results/prod/results.json
python3 -m ml2 validate-submission --input ml2/data/prod.raw.json --submission results/prod/results.json --split prod
```

`--purpose control` задаёт общий бюджет 2700 секунд (45 минут). Каждый запрос
ограничен оставшимся временем; после его истечения оставшиеся ID сохраняются как
ошибки. При `--resume` отсчёт продолжается от исходного `created_at`, не обнуляется.
Это резерв времени для экспорта и Git, **не гарантия десяти успешных оценок**.
Можно явно задать `--deadline-seconds`; не расходуйте весь час на модель.

Для повторного запуска/экспорта используйте новый путь: существующие результаты
не перезаписываются. После проверки выберите итоговый файл и поместите его в
предписанный путь. Не переносите в Git `ml2/data` или все `ml2/runs`.

Перед сдачей проверить оба файла и выполнить commit/push именно финальных результатов.
Утилиты `ml2` сами не делают commit, push и публикацию. Локального файла или commit
недостаточно: организаторы должны видеть оба файла в согласованном репозитории до стоп-кода.

## Что проверяет адаптер

- Все исходные ID, состав DEV/PROD, отсутствие пропусков/дублей и хеши входных диалогов.
- Завершённость запусков, хеш файла предсказаний, рубрики, знаний и сведения о модели.
- Коды: `needs → discovery`, `dialogue_management → dialogue`,
  `closing → closure`, `gross_errors → critical`; остальные сохраняются.
- `evidence_turns` — позиции с 1 в исходном массиве, включая клиента, бота и события.
  Берутся цитируемые ID и заявленный моделью просмотренный диапазон.
- В `value` передаётся исходная ступень, например 7 из 10, а не её взвешенный вклад.
- Итог пересчитывается; `critical_flag` соответствует `critical`, не обнуляя балл.
- `needs_review` не превращается в `null`: весь диалог получает `status="error"`.
  Неоценённый/ошибочный диалог тоже сохраняется с исходным ID.

Вывод «валидный формат» не означает высокую точность или отсутствие ошибок обработки.
После экспорта команда показывает число `ok` и `error`.

## Звонки и неоднозначные уточнения

Последнее уточнение организаторов: для звонков можно использовать транскрипт или
адаптировать подход; звонки в большей степени нужны для интерфейса. Поэтому собственный
STT, интонации и паузы не блокируют эту версию. Все 5 звонков всё равно входят в DEV-файл.

Ранее для отсутствующего начала звонка разрешили C1=N/A, но приложение 1.0 допускает
в `contact` только boolean. Последний ответ про транскрипты не разрешает `null` явно.
Внутренняя голосовая рубрика сохраняет N/A при подтверждённом обрезанном начале;
экспорт такого случая выдаёт объяснимую ошибку, не выдумывает `false`. После явного
уточнения формата потребуется версионированное изменение адаптера и тестов.

Уточнение предмета обращения (бумага, приказ, ошибка) относится к C2; подтверждение
личности перед доступом к закрытым данным/действием — к C3. Общая инструкция о том,
где посмотреть причину отклонения, сама по себе не требует идентификации по чек-листу.
Проверка конкретного приказа клиента требует подтверждённого доступа к его данным.
Риторический ответ организатора не задаёт новый обязательный способ проверки:
ИИН/кодовое слово не придумываем, наличие авторизации не предполагаем.

В примере с отклонённой покупкой оператор без деталей утверждает, что причина в бирже,
а затем признаётся, что не знает. Это основание проверять C2 и обоснованность C4;
не превращаем его автоматически в эталон C3 или флаг C8.
