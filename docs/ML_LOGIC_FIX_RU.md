# Исправление логики выявления потребности и консультации

Состояние на 7 ноября 2026. Добавлен режим `decision-reasoned`, версия постобработки `cqa-evidence-first-v4`. Это экспериментальный режим; по умолчанию API продолжает использовать прежний оценщик.

## Что реализовано

В `backend/services/decision_reasoning.py` модель перед оценками возвращает короткий фактический разбор:

- Список содержательных запросов клиента, включая последующие вопросы.
- ID реплик клиента и отвечающих на них реплик оператора.
- Покрытие: ответ, конкретный следующий шаг, объяснение границ поддержки, частичный ответ, отсутствие ответа или неопределённость.
- Отметку, нужны ли внешние источники для проверки фактов.
- Достаточность исходных сведений, конкретные недостающие детали и реплики с уточнениями.
- Проверку применимости перед каждым решением по критерию.

Сервер передаёт отдельно начальный контекст до первой реплики человека-оператора, сохраняя также весь диалог. Валидатор запрещает ссылаться на поздние реплики как на сведения из этого начального контекста. Он проверяет существование ID, роли участников, отсутствие дубликатов, наличие ответа оператора для заявленного покрытия и временной порядок ссылок. Слова клиента не могут служить `operator_answer_ids`.

Инструкция разделяет конкретный следующий шаг и немедленное решение проблемы, полноту ответа и удовлетворённость клиента, объяснение границ поддержки и отказ от консультации. Не требует выполнять защищённую операцию сейчас, если клиент спрашивает о подготовке к будущей проверке. Продуктовые факты не считаются доказанными только со слов оператора.

В `backend/services/assessment_logic.py` реализована привязка к точным семантическим определениям исходного критерия «Выявление потребности». Если валидированный разбор указывает, что сведений хватало изначально, применяется предусмотренный этим критерием N/A. Определения распознаются по хешу ID, описания, типа, правила и условия N/A. Изменение этих полей отключает специальную привязку; веса не меняются.

Сохраняются исходный ответ и журнал `logic_adjustments`. Противоречие «сведений достаточно», но одновременно перечислены недостающие сведения, переводит начальный контекст в неопределённый и соответствующее решение в `needs_review`. Проверенная консультация и остальные критерии при этом сохраняются. Отсутствующие/неверные ID и роли по-прежнему вызывают ошибку валидации.

Меню IVR и служебные события не доказывают, что исходный содержательный запрос уже был известен. Когда до приветствия человека есть только выбор кнопок, автоматическое N/A не назначается. Для звонков остаётся задача определения границы первого содержательного запроса; консервативный результат сейчас — ручная проверка, если эта граница не подтверждена.

## Проверка на модели и повторная обработка

Первый полный вариант с фактическим разбором был прерван после трёх сохранённых ответов из десяти: выявлено противоречие между достаточностью сведений и вердиктом. Его результаты находятся в `data/runs/local-logic-20261107-v1/` и не являются полным прогоном.

Далее выполнены две ограниченные пробы `logic-targeted`: `data/runs/local-logic-targeted-20261107-v2/` и `...-v3/`. Они переоценивают только два распознанных критерия — выявление потребности и консультацию. Остальные шесть решений берутся из сохранённого предыдущего `decision-guided` на тех же семи диалогах. Проверяются совпадение release и digest модели, сохраняется хеш исходных ответов. Это реконструкция двухэтапного конвейера с повторным использованием первого этапа; в задержки и токены включён сохранённый первый вызов. Скорость первого запроса v3 могла включать ожидание завершения предыдущей пробы, поэтому сравнивать по ней производительность нельзя.

В v3 строгая проверка противоречия первоначально отклонила один диалог целиком. После исправления постобработки **те же сохранённые ответы** повторно проверены без инференса:

```powershell
.\backend\.venv\Scripts\python.exe scripts/replay_logic_assessment.py
```

Итоговый снимок: `data/runs/local-logic-replay-20261107-v4/`. Сохраняет manifest, хеши всех исходных ответов, снимок кода, отдельные эталоны, решения и отчёт. Для повторного запуска нужно указать новую пустую папку через `--output`.

| Метрика на одинаковых 7 диалогах | Исходный полный baseline | Предыдущий guided | Новая постобработка и адресная переоценка |
| --- | --- | --- | --- |
| Совпадение решений | 34/56 (60,7%) | 40/56 (71,4%) | 44/56 (78,6%) |
| Полный итоговый балл | 7/7 | 7/7 | 5/7 |

На общей паре пяти диалогов MAE новой версии — **6,15**, предыдущего guided — **6,15**, исходного baseline — **5,08**. Снижение ошибки итогового балла не подтверждено. Незавершённые решения остаются в знаменателе accuracy и не превращаются в N/A или ноль.

Неопределённость по выявлению потребности отмечена в `p1-ru-002` (противоречивые факты модели) и `p4-ru-001` (исходный контекст до приветствия не содержит содержательного запроса). Консультация в этих двух диалогах всё ещё занижена относительно эталонов: 15 вместо 20 и 5 вместо 20. Программно повышать их до эталона нельзя: нужно проверить фактическую основу и причину снижения.

Это многократно используемая DEV-выборка с подтверждённой AI-предразметкой, а не независимый тест. Структурная проверка ссылок не подтверждает их смысловую релевантность. Данные, веса и эталоны не подменялись.

## Запуск дальнейших проверок

Самостоятельный режим для полного чек-листа доступен через стандартный CLI из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m ml.run --wire-format decision-reasoned --ids p1-ru-002 --run-dir ../data/runs/logic-next-check
```

Для воспроизведения адресного эксперимента на сохранённой контрольной базе из корня проекта:

```powershell
.\backend\.venv\Scripts\python.exe -u scripts/local_improvement_experiment.py --output data/runs/logic-targeted-next --variants logic-targeted
```

Он использует только диалоги, для которых уже сохранён предыдущий guided-base; это инструмент диагностики, а не полноценный новый API-конвейер. Полный вариант `decision-reasoned` и адресный вариант с сохранёнными шестью критериями нужно оценивать раздельно. При увеличении выборки сначала проверяйте лимит контекста: отдельное поле начального контекста добавляет объём, текст не обрезается.

Следующие задачи: обоснование каждого снижения консультации конкретным незакрытым вопросом либо проверенным фактическим нарушением; продуктовые материалы для спорных фактов; корректная граница исходного запроса в звонках; затем более широкая проверка при сохранении покрытия и MAE в отчёте.
