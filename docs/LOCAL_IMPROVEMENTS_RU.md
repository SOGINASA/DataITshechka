# Улучшения локального оценщика и редкие грубые ошибки

Следующий этап — фактический разбор запросов и программное согласование N/A — описан в [ML_LOGIC_FIX_RU.md](ML_LOGIC_FIX_RU.md). Приведённые ниже результаты относятся к предыдущим кандидатам.

## Эксперимент 7 ноября 2026

Добавлен экспериментальный формат `decision` в `backend/services/ollama.py`. Вместо двух зависимых полей `status` и `value` модель возвращает одну строку `answer`. Тип, допустимость N/A, шкалы и полярность флага проверяются кодом, затем решение преобразуется в прежний API-контракт. Новые критерии поддерживаются через переданный чек-лист. Ссылки на реплики и расчёт балла проходят прежнюю валидацию.

Формат включается явно аргументом `wire_format='decision'`; производственный вызов пока сохраняет прежнее поведение. Это кандидат для измерения, не доказанное улучшение по умолчанию. Вариант `legacy-reversed` меняет только порядок ветвей `anyOf`, сохраняя прежний текст инструкции. `decision-guided` добавляет условные учебные примеры для N/A, завершения и флага нарушения; они написаны отдельно, без копирования DEV-текстов и эталонов. Правила переданного чек-листа имеют приоритет над примерами.

Запуск ограниченной диагностики:

```powershell
.\backend\.venv\Scripts\python.exe -u scripts/local_improvement_experiment.py
```

Отдельная проверка уточнённой инструкции:

```powershell
.\backend\.venv\Scripts\python.exe -u scripts/local_improvement_experiment.py --output data/runs/local-improvements-20261107-guided-v1 --variants decision-guided
```

Для последующего прогона произвольной выборки стандартный `python -m ml.run` из папки `backend` поддерживает `--wire-format decision-guided`, а также `legacy`, `legacy-reversed` и `decision`. Нужны отдельный `--run-dir` и подходящие `OLLAMA_NUM_CTX`/`OLLAMA_NUM_CTX_CALL`; сам эксперимент задаёт расширенные лимиты независимо от `.env`. В manifest сохраняются фактический системный prompt и схема через их хеши/снимки, версия формата и новые модули. После изменения исходников продолжение старого эксперимента намеренно запрещается: используйте новую папку или исходный снимок кода.

Протокол: 6 чатов с чередованием EN/KZ/RU и один RU-звонок; обратный порядок старой схемы на первых трёх чатах; отдельный вызов только для флага грубых ошибок на всех 8 известных положительных и 8 отрицательных примерах. Для каждого вызова используется полный транскрипт, без эталонных решений в контексте модели. Голосовая политика — замороженная v1 для сопоставимости. Метаданные, ответы и снимки кода — `data/runs/local-improvements-20261107-v1/`.

Контекст кандидата: 28672 для чатов и 45056 для звонков, выход до 4096 токенов, `qwen3:4b`, `think=false`, температура 0. Все 60 чатов и 5 звонков проходят предварительную проверку вместимости без обрезки текста. Это проверка размера, а не подтверждение успешного инференса всех 65. В исходном полном прогоне два диалога получили 422 при меньшем контексте. Различие размеров контекста учитывается при сравнении задержек.

Короткая диагностика не является независимым тестом. Выборка грубых ошибок намеренно обогащена нарушениями; её accuracy и precision нельзя переносить на естественную частоту потока. Сохранённые ошибки и незавершённые ответы не подменяются успешными. `--resume` требует неизменных исходников и настроек.

## Итог ограниченной диагностики

Все запланированные вызовы завершены; после завершения модель выгружена из VRAM. Производственный режим по умолчанию не переключался на кандидата.

| Проверка | Исходная версия на той же выборке | Кандидат |
| --- | --- | --- |
| Только обратный порядок старых ветвей, 3 чата | 15/24 | 15/24 |
| Одно решение вместо status/value, 7 диалогов | 34/56 (60,7%) | 34/56 (60,7%) |
| Одно решение + уточняющие примеры, те же 7 диалогов | 34/56 (60,7%) | 40/56 (71,4%) |
| Только флаг грубых ошибок, 8 положительных + 8 отрицательных | Найдено 1/8, ложных срабатываний 0/8 | Найдено 2/8, ложных срабатываний 0/8 |

У уточнённой инструкции 5 корректных N/A из 14 эталонных против 0 у исходной версии. Однако MAE итогового балла **ухудшился с 7,13 до 16,47** на общей паре всех семи диалогов. Больше точных ответов по отдельным критериям не означает меньшую ошибку взвешенного итога. Простое изменение формата также не улучшило итог: MAE на общей паре шести диалогов — 28,21 против 5,06; на седьмом у кандидата итог неполный. Поэтому оба новых режима остаются экспериментальными.

Результат проверки порядка ветвей не подтвердил, что перестановка сама по себе устраняет систематические положительные ответы. Режим с примерами помогает идентификации (5/7 правильных), но выявление потребности (1/7) и завершение (2/7) остаются слабыми; звонок — 3/8. Следующий шаг — разбор этих ошибок и взвешенного итога до полного прогона или обучения. По грубым ошибкам нужен разбор шести оставшихся пропусков; выигрыш одного примера не подтверждает устойчивое обобщение.

Подробные приватные отчёты: `data/runs/local-improvements-20261107-v1/report.json`, `data/runs/local-improvements-20261107-guided-v1/report.json`. Для корректного сравнения MAE в них отдельно указаны число общих пар и ошибки на этих парах. Исходные снимки кода инференса — `code/`; использованный для итогового парного анализа снимок — `analysis-code/`. В backend прошли 140 тестов.

## Что означает «вычесть из единицы»

Для двух взаимоисключающих и исчерпывающих классов:

```text
P(есть нарушение | диалог) = 1 − P(нет нарушения | диалог)
```

Но это не способ получить вероятность из любого числа. `1 − accuracy` — частота ошибок предсказателя на выборке, а не вероятность нарушения в конкретном диалоге. Итоговый балл оператора, ответ LLM «уверен на 90%», сходство с нормальными разговорами и anomaly score также не являются вероятностями класса. Сам факт необычности разговора не доказывает ни одно из трёх нарушений.

В DEV 8 положительных и 57 отрицательных примеров. Предсказатель «нарушений нет всегда» получил бы 87,69% accuracy и 0% recall. Исходная 4B: TP=1, FP=0, FN=7, TN=55 и два необработанных отрицательных диалога. Recall=12,5%; precision=100% основан только на одном срабатывании. Это не подтверждает надёжность. Один положительный пример меняет recall на 12,5 процентного пункта.

По основаниям в текущих пояснениях положительные случаи предварительно распределяются так: 4 предложения частных платных услуг, 3 раскрытия информации о конкретном счёте, 1 оскорбление. Это анализ пояснений, а не новая независимо подтверждённая разметка подтипов. Для обучения распознаванию оскорблений одного примера особенно мало; примеры по языкам и каналам также покрыты неравномерно.

Добавлены `backend/ml/critical.py` и скрипт аудита:

```powershell
.\backend\.venv\Scripts\python.exe scripts/audit_critical_errors.py
```

`data/runs/critical-audit-20261107/report.json` содержит confusion counts, precision, recall с учётом неразрешённых случаев, F1/F2 и очередь проверки. Для дальнейшей детализации предложены три подтипа: оскорбление, частная платная услуга, раскрытие конфиденциальных данных. Поля подтипов пока пустые: они не объявлены человеческой разметкой и не меняют существующие подтверждённые метки.

## Как готовить обучение

1. Сначала проверить, помогает ли исправление формата и отдельная оценка флага. Это не требует обучения весов модели.
2. Размечать событие и доказательства: тип нарушения, реплики оператора, существенный контекст, отсутствие/наличие нарушения и причину неопределённости. Невыполнение идентификации само по себе не доказывает раскрытие данных.
3. Расширять положительные сценарии по всем трём основаниям, языкам и каналам. Добавлять сложные отрицательные примеры: ругается клиент; оператор цитирует жалобу; предлагает официальную платную услугу компании; даёт общедоступную информацию. Проверять их человеком.
4. Синтетика полезна для покрытия конкретных пробелов после проверки. Перефразировки, переводы и пары «до/после изменения нарушения» одного сценария должны попадать в одну группу при разделении данных. Синтетика для обучения не должна превращаться в независимый тест или калибровочный набор.
5. После расширения данных можно обучить отдельный бинарный/многометочный классификатор или адаптер LLM. Для дисбаланса пробовать веса классов или выборку положительных примеров только внутри train. Порог выбирать по precision/recall и доступной нагрузке на ручную проверку, не по accuracy.
6. Если нужны именно вероятности, калибровать численный выход классификатора на отдельной, репрезентативной размеченной выборке. Проверять калибровочные кривые, Brier/log loss вместе с precision/recall и AP. Выравнивание классов при обучении не означает, что в реальном потоке нарушения встречаются в 50% случаев; искусственно сбалансированный набор нельзя использовать для обоснования реальных вероятностей без поправки на частоты и независимой проверки. Восьми DEV-нарушений недостаточно, чтобы обосновать надёжные проценты; обучение вероятностной модели и калибровка сейчас не заявляются.

Приоритетом остаётся распознавание определённых чек-листом событий с проверяемыми доказательствами. Система обнаружения аномалий может направлять необычные диалоги на просмотр, но её выход нельзя автоматически выдавать за вероятность грубой ошибки.

Источники: [калибровка вероятностей, scikit-learn](https://scikit-learn.org/stable/modules/calibration.html), [метрики для несбалансированных классов, Google ML Crash Course](https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall).
