# План обучаемой модели и резервной оценки

Обновлено: 8 ноября 2026

## Роли моделей

- **Основная модель** — наша обучаемая модель, которую предстоит выбрать и обучить
  после подготовки пригодного набора и зафиксированного теста.
- **Резервная модель (fallback)** — текущий локальный Ollama/Qwen. Она вызывается,
  если основная модель недоступна/вернула невалидный ответ или её уверенность ниже
  порога, выбранного по validation. Сейчас каскад ещё не реализован: приложение
  вызывает Ollama напрямую, а API организаторов служит источником диалогов, не API
  inference модели.
- Сохранять для каждой оценки: модель и версию, confidence, причину переключения,
  обе оценки (если fallback запускался), длительность и итог ручной проверки.
  Confidence нельзя принимать за самооценку LLM: порог выбирается по validation
  через калибровку и кривую «покрытие / ошибка». До этого fallback включается только
  при технической ошибке, а низкая уверенность отправляет оценку человеку.

## Что уже известно о данных

- **Жёсткое ограничение эксперимента:** весь набор DEV из 65 ID — закрытый тест. Он
  не используется для обучения, генерации тренировочных примеров, настройки промпта,
  выбора гиперпараметров или порогов. `backend/ml/protected_test_ids.json` закрепляет
  эти ID, а exporter отвергает release с пересечением. При каждом сравнении на DEV
  фиксируются версия модели и конфигурации до запуска.
- В `case/api.txt` находится GET-ссылка на API с параметром `group_id=DEV`.
  Student Guide поясняет: DEV — набор для разработки (65 записей); другой `group_id`
  для контрольного набора сообщают отдельно. По Guide контрольные диалоги открываются
  на контрольном этапе, через 23 часа после старта.
- Я запросил DEV через эту ссылку: API вернул 65/65 записей — 60 чатов, 5 звонков;
  языки: RU 35, KZ 15, EN 15. Ссылки на аудио удалены из локального снимка, так как
  текущий ML-пайплайн оценивает транскрипты, а не звук. Снимок лежит в
  `data/raw/dev.json`; каталог исключён из Git.
- `annotation/README.md` описывает состав DEV: 60 синтетических чатов и 5 реальных
  звонков. Разговоры не являются 65 независимыми реальными клиентскими кейсами.
- Документация прежней разметки описывает 520 предварительных AI-меток и 484 решения,
  которые подтверждались в прошлой рабочей копии. Эти файлы не закоммичены и сейчас
  отсутствуют; пересоздавать их из DEV или подменять ими закрытый тест запрещено.
  Текущая рабочая БД с 9 чатами/8 оценками/0 ревью не является источником обучающих
  меток. DEV используется только для итогового сравнения.
- Последний зафиксированный генеративный baseline: 55/80 точных меток (68,75%) на
  10 диалогах; это диагностический dev-срез, не независимый тест. Особенно слабы
  N/A (0/16) и завершение (4/10). До сравнения с обучаемой моделью эти значения
  нельзя считать доказательством качества на новых диалогах.
- Организаторский API — подписанный источник transcript-данных, не endpoint готовой
  модели. Контрольный ID не нужен для первого шага обучения на DEV; он нужен позже для
  финальной независимой проверки. Не подставлять случайные имена групп: использовать
  только значения, указанные в Guide/API или сообщённые организаторами.

## Данные для первого обучения

Публичные источники не заменяют целевые метки оценки качества:

1. `AmazonScience/MASSIVE`: 19,521 короткая размеченная команда на язык для intent/slot
   classification; включает English и Russian, но не Kazakh. Лицензия CC BY 4.0.
   Полезен для вспомогательного теста языкового понимания/классификации, но это
   однофразовые запросы голосовому помощнику, а не разговоры поддержки и не оценки QA.
2. `mangi-llm/kazakh-customer-support-qa`: 406 казахских вопрос–ответов, лицензия
   CC BY 4.0 с атрибуцией. Полезен как вспомогательный источник казахских формулировок
   поддержки, но не содержит меток критериев операторского качества.
3. `KazParC`: параллельный корпус казахский–русский–английский, опубликован по CC BY 4.0.
   Можно использовать для проверки языкового покрытия/переводных вариантов, но не
   переносить автоматически метки качества между переводами без ручной проверки.
4. NCSpeech Banking: казахские и русские банковские фразы; коммерческая/исследовательская
   лицензия выдаётся по запросу. Это преимущественно записанные отдельные реплики, не
   размеченные оценки диалогов; до получения условий и лицензии не скачивать для обучения.
5. Публично заявленный Russian Call Center Speech Dataset (832 часа): README заявляет
   коммерческое использование, но это аудио без метаданных/целевых оценок; лицензия
   запрещает перераспространение. Он может быть полезен для ASR/голоса, но не для
   обучения нашей модели оценки без транскриптов, правовой проверки и ручной разметки.

Основной источник супервизии — реальные разговоры через выданный API и проверенные
человеком решения по официальному чек-листу. Нужно получить разрешённую группу данных,
зафиксировать snapshot и права использования, затем собрать независимую перепроверку.
Похожие сценарии, переводы и перефразировки должны целиком оставаться в одном split.

## Подготовленный запуск LoRA на Mac

В `backend/.venv` уже установлены MLX-LM и модель-база `mlx-community/Qwen3-1.7B-4bit`.
После создания отдельного обучающего корпуса и scenario-group split команда экспорта
подготовит JSONL, а скрипт `backend/ml/train_mac.sh` запустит LoRA с маскированием
промпта, batch size 1, gradient checkpointing и ограничением длины 4096 токенов.
Путь результата должен быть новым и версионированным; готовый adapter появится только
после реального завершения обучения.

Пример полного запуска из корня проекта:

```sh
cd backend
.venv/bin/python -m ml.export_sft \
  --release ../data/releases/dev-reviewed-v1 \
  --splits ../data/splits/scenario-v1.json \
  --out ../data/training/scenario-v1
cd ..
backend/ml/train_mac.sh data/training/scenario-v1 data/models/qwen3-1.7b-lora-v1
```

`data/raw/dev.json` — только тестовые транскрипты; обучающий builder и SFT exporter
защищают их ID от попадания в обучающий релиз. Публичные intent/QA корпуса не содержат
готовых меток по нашему чек-листу, поэтому запущенный ниже отдельный синтетический
пилот явно отделён от human-reviewed production release. Его адаптер экспериментальный;
качество на DEV смотрим один раз после фиксации модели и промпта.

## Отдельный пилот слабой разметки

Для первого обучающего прогона добавлен `backend/ml/build_weak_cqa.py`. Он читает
публичные train-источники (не их test), создаёт локальные диалоги на основе вопросов
и ответов, затем вносит заранее определённые правильные и ошибочные действия оператора.
Метки выводятся из конструкции варианта: приветствие/представление, уточнение, полнота,
вежливость, ясность, завершение, идентификация и грубые нарушения. Перевод казахских
вопросов на русский и английский выполняется локальным Qwen и маркируется как машинный.

Это синтетические слабые метки, не ручная проверка реальных диалогов. Их назначение —
технический LoRA-пилот и проверка, способна ли модель воспроизводить явные правила.
По результату нельзя заявлять производственную точность. Сценарии одной темы и их
переводы целиком относятся к одному train/valid/test split. 65 DEV ID экспортёр
блокирует независимо от сценария.

Фактически собранный `weak-cqa-v1`: 16 казахских тем с машинными версиями на русском и
английском плюс 128 выбранных русских исходников, каждый развёрнут в 16 контролируемых
вариантов. Всего 2 816 синтетических примеров: 2 176 train, 320 validation и 320
синтетический test. Последний нужен только для диагностики этого пилота и не заменяет
запечатанный набор из 65 DEV диалогов.

Обучение `mlx-community/Qwen3-1.7B-4bit` на M4 было прервано при выключении Mac после
125 из 300 шагов: первые 25, затем ещё 100 после resume. Последний сохранённый checkpoint
лежит в `data/models/qwen3-1.7b-weak-cqa-v1/0000100_adapters.safetensors` (нумерация checkpoint
локальна для resume-запуска). На первом отрезке validation loss снизился с 1.157 до
0.140 (25 батчей); при продолжении используются только 2 validation batch и проверка
раз в 100 шагов из-за длительности Metal-вычислений. Значения validation из этих режимов
напрямую не сравниваются. Файл адаптера структурно цел, но 300-шаговое обучение и оценка
качества не завершены.

На checkpoint 125 выполнен один прямой MLX inference на `gen-ru-short-004` (17.2 секунды;
ответ сохранён локально рядом с adapter). Модель дала несколько правдоподобных решений,
но привязала контакт к реплике бота `m2`, а не оператора `m7`, привела клиентские реплики
как доказательства ответа оператора и во всех критериях ограничила `reviewed_range` сообщениями
`m1`–`m4`, хотя использовала `m11` для завершения. В объяснении эмпатии также неверно
сказано, что неудобства не было. Ответ дополнен `<think>` перед JSON и не годится напрямую
для текущего строгого JSON-парсера. Это явные ошибки основания/формата; дальнейшее обучение
на том же синтетическом наборе вслепую не обосновано. Сначала нужно поправить примеры,
обеспечить полный диапазон проверки и чистый JSON decoder, затем оценивать заново.

## Следующие шаги после пилота

1. Восстановить локальные AI-разметки, описанные в README, и использовать их только как
   очередь подсказок. Независимо проверить их по официальному чек-листу; для пяти звонков
   отдельно прослушать аудио, если оцениваются акустические признаки. Не включать
   подписанные URL аудио в артефакты обучения.
2. Проверить спорные метки вторым человеком: сначала завершение, N/A, консультация,
   выявление потребности;
   для каждого решения сохранить основание и ID реплик, а спорное — отдать второму
   независимому аннотатору.
3. Создать scenario groups до разделения. Если после этого данных мало для надёжного
   test, набрать дополнительные реальные примеры; не дробить переводы одного кейса.
4. Зафиксировать held-out test, который не используют для промптов, синтетики, порогов
   или выбора модели. Сравнить на нём: текущий Qwen baseline, основную модель без
   обучения, затем обученную версию. Отчёт — exact match / macro-F1 по критериям,
   ошибки N/A, precision/recall критических нарушений, калибровка confidence,
   латентность и разрезы RU/KZ/EN и chat/call.
5. Первый обучающий эксперимент — лёгкий классификатор/ранкер по критериям, если
   объём чистых меток и согласованность это позволяют. Если нужен LLM для цитат и
   объяснений, отдельно сравнить parameter-efficient fine-tuning на train и оставить
   проверку/эскалацию человеку. Не обучать с нуля.
6. После подтверждения качества подключить каскад: trained primary → local Qwen
   fallback на техническую ошибку или низкую калиброванную уверенность → ручная
   проверка, если резерв тоже неуверенен. Никакая частичная оценка не выдаётся как
   завершённая.

## Оценка обучения на MacBook Air M4

На этой машине M4 с 16 GB unified memory. MLX-LM поддерживает LoRA/QLoRA, gradient
checkpointing и уменьшение batch/числа обучаемых слоёв для экономии памяти. Для
квантованной модели 1–3B и коротких примеров технический запуск на этом Mac реалистичен;
8B QLoRA с длинными транскриптами на 16 GB будет тесным и не является первым выбором.

Первый запуск на синтетическом наборе дал около 21 токена/с после первичной подготовки
Metal. Validation на 25 батчах заняла 335 секунд, поэтому текущий прогон на 300 шагов
может занять часы. Это измерение конкретного запуска, а не оценка качества модели.
Предыдущие ориентиры до замера:

- установка MLX-LM и загрузка совместимой базы 1–3B: примерно 15–60 минут при хорошем
  интернете, больше при медленном скачивании;
- короткий LoRA pilot: от десятков минут до нескольких часов в зависимости от длины
  последовательностей и частоты validation;
- несколько вариантов параметров + контроль инференса: примерно 1–3 часа;
- формирование gold-разметки 65 диалогов и независимая перепроверка — основная работа,
  ориентировочно несколько рабочих дней, а не минуты GPU.

При текущем наборе самообучение с нуля исключено, а LoRA будет экспериментом на малом
и преимущественно синтетическом наборе. Чтобы оценить выигрыш на реальных обращениях,
нужны проверенные метки и больше разрешённых реальных диалогов; независимый контрольный
набор следует оставить нетронутым до финального сравнения. На нём запускается только
финальная оценка, не обучение.

Локальный exporter для будущего SFT уже подготовлен: `backend/ml/export_sft.py` принимает
только immutable release и явный split-манифест `{"train": [...], "valid": [...],
"test": [...]}`. Он отвергает неeligible разметки, дубликаты, пропущенные и лишние ID,
а `test.jsonl` пишет отдельно. До появления восстановленной, проверенной разметки и
содержательного group-aware split SFT-команда намеренно не запускается.
