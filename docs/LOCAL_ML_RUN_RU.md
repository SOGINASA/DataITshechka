# Локальная модель и первый измеримый прогон

Для RTX 4050 Laptop с 6 ГБ VRAM подготовлена стартовая конфигурация `qwen3:4b`.
Это baseline для измерения качества RU/KZ/EN. Дообучение и дополнительная синтетика
до анализа ошибок не нужны. Модель занимает около 2,5 ГБ; большой контекст требует
дополнительной памяти. Локальный профиль использует Flash Attention и кэш q8_0;
контекст 24K использован в первом контрольном прогоне. Полный DEV-прогон выявил,
что после расширения промпта `p1-ru-010` превышает консервативный лимит и получает
422 до обращения к модели. Для него нужен больший контекст, например 28672,
с отдельной проверкой памяти и времени. Часть слоёв всё ещё может перейти на CPU.
С кэшем f16 и контекстом 32K первый диалог занял 175 секунд;
профиль q8_0/24K заметно сократил это время. Точные результаты — в отчёте прогона.

## Установка и запуск

Все команды ниже выполняются в PowerShell из корня репозитория.

```powershell
# Первый запуск: официальный portable Ollama и модель.
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\local_model.ps1 -Action setup
# При следующих запусках:
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\local_model.ps1 -Action start
```

Runtime закреплён на `v0.40.15`, SHA256 архива проверяется по опубликованному
GitHub release. Runtime, модели и логи находятся в `.tools/` и исключены из Git.
При первом старте Ollama также создаёт служебный ключ в пользовательской `.ollama`.
API слушает только `127.0.0.1:11434`. Внешний платный API-ключ не нужен.
Для установки и скачивания нужен интернет; после скачивания инференс локальный.

Настройки в локальном `backend/.env`:

```dotenv
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen3:4b
OLLAMA_TIMEOUT=300
OLLAMA_NUM_CTX=24576
OLLAMA_NUM_PREDICT=4096
OLLAMA_NUM_CTX_CALL=40960
OLLAMA_NUM_PREDICT_CALL=3072
OLLAMA_THINK=false
```

Исходный корневой `.env` с URL организаторов не меняется. Если адрес API нужен
для новых импортов, задайте `FREEDOM_API_URL` в `backend/.env`. Сохранённый DEV
можно импортировать без сетевого обращения:

```powershell
.\backend\.venv\Scripts\python.exe -m flask --app backend/app.py init-db
.\backend\.venv\Scripts\python.exe -m flask --app backend/app.py import-dataset --file data/raw/dev.json
```

Если Python-окружения ещё нет:

```powershell
python -m venv backend/.venv
.\backend\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
```

Backend в отдельном терминале:

```powershell
.\backend\.venv\Scripts\python.exe backend/app.py
```

Frontend в другом терминале; локальная сборка обязательно направляется на локальный API:

```powershell
cd frontend
npm.cmd ci
$env:PUBLIC_API_URL='http://127.0.0.1:6767/api'
npm.cmd start
```

Интерфейс: `http://localhost:3000`; здоровье API: `http://127.0.0.1:6767/api/health`.
Адрес по умолчанию в исходном frontend указывает на удалённый сервер, поэтому
переменная `PUBLIC_API_URL` нужна именно перед локальной сборкой.

## Сравнение с подтверждённой разметкой

Из папки `backend`:

```powershell
cd backend
# Проверка всех 65 диалогов / 520 меток; модель не вызывается.
.\.venv\Scripts\python.exe -m ml.run --prepare-only
# Чек-листы из снимка плюс новая голосовая политика в локальную БД.
.\.venv\Scripts\python.exe -m ml.seed --additional-rubric ../annotation/checklist.voice.v2.json
# Первые 10 чатов, распределённые между EN/KZ/RU без подбора по ответам.
.\.venv\Scripts\python.exe -m ml.run --limit 10 --run-dir ../data/runs/qwen3-4b-control-v1
# Затем все 65 в отдельном эксперименте.
.\.venv\Scripts\python.exe -m ml.run --run-dir ../data/runs/qwen3-4b-dev-v1
# Продолжение прерванного запуска с неизменными настройками.
.\.venv\Scripts\python.exe -m ml.run --limit 10 --run-dir ../data/runs/qwen3-4b-control-v1 --resume
```

Для конкретных разговоров используйте `--ids p1-en-001,p1-kz-001,p1-ru-001`.
`--ids` задаёт точные ID; `--limit` распределяет чаты по языкам, затем добавляет звонки.
Не используйте один run-dir для разных выборок или настроек. Resume пропускает
все сохранённые строки, включая ошибки. Для повторной проверки исправленной ошибки
создайте новый run-dir с нужными `--ids`: это сохраняет историю эксперимента.

Результаты находятся в игнорируемой Git папке `data/runs/<имя>/`:

- `run.json`: digest модели, настройки, версии и хеши промпта/адаптера/снимка;
- `inputs.json`: только входы и рубрики, без эталонных ответов и аудиоссылок;
- `references.json`: эталоны, отдельно от запросов к модели;
- `predictions.json`: реальные ответы или явные ошибки, атомарно после каждого случая;
- `metrics.json`: точность с фиксированным знаменателем, ошибки, отказы, N/A,
  precision/recall нарушений, MAE шкал и итогового балла, количество сопоставимых
  диалогов, время и доступные счётчики токенов, список расхождений.

На один диалог — один вызов без few-shot и без автоматического повтора. Ошибки JSON,
неверные ступени и несуществующие ID не превращаются в успешную оценку.
Отказ модели и ошибка остаются в знаменателе. При недоступности сервиса прогон
останавливается после сохранения ошибки. Длинный контекст не обрезается: возможен 422.
Не увеличивайте контекст до предела без проверки памяти и времени на одном разговоре.
Одного профиля 24K для звонков недостаточно. В локальном `.env` настроен отдельный
профиль: контекст 40960 и выход до 3072 для `channel=call`. После расширения промпта
полный прогон выявил 422 на самом длинном `p4-ru-004`; ему нужен больший лимит,
например 45056. Проверку размера нужно повторять после изменения промпта. Расход RAM и доля
слоёв на CPU увеличиваются; время звонка нужно измерять отдельно. Если call-настройки
не заданы, используется основной профиль: длинные звонки дадут явный 422.
Нельзя молча урезать текст или выдать результаты чатов за качество звонков.

Сырые финальные ответы для диагностики находятся в `responses/`. Скрытые рассуждения
модели не сохраняются. JSON schema связывает каждый ID с его типом, статусом и
допустимыми значениями; проверка на сервере остаётся обязательной.

Реальный первый результат: [ML_BASELINE_RESULTS_RU.md](ML_BASELINE_RESULTS_RU.md).
Технически завершены 10/10 чатов; точность 55/80, проблема N/A остаётся открытой.

Все 65 относятся к **development**, независимого test пока нет. Это проверенная
пользователем исходная AI-разметка; повторную независимую экспертизу она не заменяет.
Результаты звонков, эталоны которых проверялись с аудио, выделяются отдельно:
сама модель получает только текст. Продуктовые материалы брокера пока не подключены.

## Уточнение о незаписанном приветствии

Новая версия: `annotation/checklist.voice.v2.json`, `voice-adapted-2`.
Если начало с приветствием не попало в запись, C1 можно отметить N/A, указав
основание неполноты. Если начало записано и приветствия нет — «Нет».
Одна ошибка ASR или отсутствие слова «здравствуйте» ещё не доказывают обрезанную запись.
При недостатке данных о границе — «не уверен» до проверки аудио.
При N/A вес C1 исключается из знаменателя; итог не получает автоматические 10 баллов.

`python annotation/upgrade_voice_policy.py` переносит пять звонков в отдельное
пространство v2, сохраняя прежние подтверждения неизменённых ответов. Для `p4-ru-002`
подготовлено предложение N/A, **не подтверждённое человеком**; остальные 39 меток
сохраняют прежние подтверждения. Очередь: `data/exports/voice-v2-review-queue.json`.
В инструменте разметки выберите профиль звонков **v2** и прежнего автора разметки звонков.
Если сервер уже был запущен до добавления профиля, перезапустите `python annotation/server.py`.

В текущем локальном API сохранены две реальные модельные оценки для просмотра:
чат `p1-en-001` и звонок `p4-ru-002`. Обе требуют человеческой проверки.
Длинный звонок прошёл через API за 88,80 сек; это не подтверждение правильности
его оценок или работоспособности всех звонков.

Снимок `dev-reviewed-v1` и голосовая v1 остаются неизменными. Текущий baseline
использует их исходную политику. Нельзя сравнивать предсказания по v2 с эталонами v1
как с одинаковой задачей. После проверки v2 нужен отдельный снимок для следующих
голосовых экспериментов; десять контрольных чатов этим изменением не затронуты.
