# Продолжение реализации после завершения разметки

Состояние проверено 7 ноября 2026 года в текущем рабочем дереве.

## Актуальное исправление от 8 ноября 2026 года

Описанные ниже приватные файлы разметки и `dev-reviewed-v1` находились в прежней
локальной копии и не были включены в Git. В текущем checkout их нет. Предыдущие
счётчики и команды в этом документе — историческая запись, их нельзя использовать как
наличествующий train release. Пользователь закрепил все 65 DEV ID как закрытый test:
не обучать, не размечать для train и не подбирать на них промпты/пороги. Список ID
хранится в `backend/ml/protected_test_ids.json`; экспорт SFT блокирует пересечение.
Для обучения требуется новый отдельный корпус и split по семействам сценариев.

## Последовательность продолжения

### 1 Запустить перенесённый код

Код и зависимости подготовлены. Следовать командам локального запуска в новом руководстве.
Настройки модели находятся в `backend/.env`; корневой `.env` с URL данных не меняется.
При локальной сборке frontend задать `PUBLIC_API_URL=http://127.0.0.1:6767/api`.

### 2 Согласовать адаптер данных и ответов

Не менять уже проверенную разметку ради названий backend. Нужен явный адаптер:

| Наша разметка | Контракт из нового документа | Проверка |
| --- | --- | --- |
| score | scored | Сохранить исходную ступень, не подменять её весом |
| na | not_applicable | Не смешивать с недостаточностью данных |
| uncertain | needs_review | Отдельный статус критерия, не общий статус согласования |
| turn_id | message_id | Сохранить ID либо таблицу соответствия, не угадывать по индексу |
| checked_span | reviewed_range | Передать обе включённые границы |
| audio_url | recording_url | Использовать в UI; не отправлять подписанную ссылку текстовой модели |
| critical_errors: pass | C8 value=true, status=fail | Да означает грубое нарушение |
| critical_errors: fail | C8 value=false | Статус и имя ID сверить с реальным backend |

Остальные ID критериев тоже сверить с перенесённой конфигурацией: в документе упоминается
gross_errors, а текущий ID — critical_errors. Не сопоставлять новые критерии только по названиям.
Смысл C8 должен зависеть от is_critical и значения, а не от универсального предположения
«pass всегда означает хорошую работу».

До модели проверить контрактными примерами: Да, Нет, ступень, N/A, неопределённость,
грубая ошибка, отсутствующее действие и итог с перераспределением весов.

### 3 Запустить первую настоящую оценку

Использовать один доступный мультиязычный model_id, полный диалог и динамический чек-лист.
Начать с concurrency=1 и небольшого набора 6–10 development-диалогов, включив RU/KZ/EN,
звонок, N/A и C8. Эталонные ответы модель не получает.

При Ollama JSON Schema передаётся через format; после ответа всё равно нужна проверка
семантики, ступеней и ссылок. Поддержка формата описана в
[официальной документации](https://docs.ollama.com/capabilities/structured-outputs).
Адресный повтор — максимум один по правилам нового плана. Ошибка или отказ остаётся
явным результатом задания; готовая разметка не используется как запасной ответ модели.

Пакетный оценщик сохраняет `predictions.json`, `run.json`, `metrics.json` с model_id,
digest, параметрами, хешами промпта/адаптера/чек-листов, временем, токенами и ошибками.
Сохранение атомарное после каждого диалога, доступен resume с неизменными настройками.
Первый эксперимент выполняется без автоматического повтора; после анализа ошибок
можно добавить максимум один адресный повтор как отдельный измеряемый эксперимент.

### 4 Прогнать все 65 и построить отчёт

Первый эксперимент A — один запрос без few-shot-примеров и без сложного retrieval.
Получить все результаты и ошибки, затем сравнить с references.jsonl.

- Основная внутренняя метрика: точные решения по критериям на фиксированном знаменателе;
  техническая ошибка и отказ не засчитываются как правильный ответ.
- Отдельно считать N/A, пропуски/ложные C8, точные ступени C4/C6 и корректность ссылок.
- MAE итогового балла показывать вместе с долей полных оценок и количеством сопоставленных пар.
- Вывести RU/KZ/EN, чат/звонок, время p50/p95 и фактические затраты всего пути.
- Для звонков отдельно отметить несовпадение условий: текстовая модель не слышит аудио,
  которое человек использовал в трёх эталонных оценках.

Это диагностическая оценка на development, а не результат на независимом контроле.
Для сравнения few-shot/моделей сначала назначить scenario_group и зафиксировать внутренние срезы.
Не менять несколько гипотез сразу и не скрывать провалы модели из знаменателя.

### 5 Подключить сквозной интерфейс

После первого измеримого прогона связать frontend с реальным API:
новый диалог → чек-лист → запуск → доказательства → апелляция → решение → пересчёт → перезагрузка страницы.
Backend хранит исходный и финальный результаты, UI показывает серверную арифметику и явные ошибки.
Прежние демо-оценки не должны подменять реальные результаты.

Показать изменение формулировки/шкалы/N/A через интерфейс с новой оценкой без изменения кода.
Затем добавить сравнение сохранённых версий, как описано в новом документе.
Для точного перехода к аудиофрагменту сначала подтвердить связь ISO-времени с позицией записи:
удержание и приостановки записи не позволяют автоматически считать их одним таймером.

### 6 Улучшать после анализа ошибок

Подключить продуктовые документы с версиями для C4 и измерить изменение ошибок.
Потом рассматривать few-shot, другую модель, retrieval и эксперимент STT.
Дообучение, массивную синтетику и акустический классификатор пока не начинать.
Польза STT должна проявиться в качестве CQA при том же оценщике, а не только в более красивом тексте.

## Ближайший проверяемый результат

Работающий переносимый backend получает inputs.jsonl и checklists.json, реально вызывает
выбранную модель и сохраняет predictions.jsonl плюс metrics.json по фиксированному набору.
Для каждой ошибки видна причина. До этого улучшать промпт или строить обучение преждевременно.
