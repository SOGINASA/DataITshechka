# Ручная разметка CQA

Локальный инструмент на Python 3.10+, без сторонних библиотек, API-ключа и npm.
Он читает `data/raw/dev.json` и открывает интерфейс для человека-разметчика.
Он не вызывает LLM, не присваивает ответы автоматически и не обучает модель.
Итоговый балл вычисляется обычным кодом по введённым ответам и официальным весам.

## Запуск

Из корня репозитория:

```powershell
python annotation/server.py
```

Откройте http://127.0.0.1:8765. Остановка — Ctrl+C в терминале.
При занятом порте: `python annotation/server.py --port 8766`.
Работа не требует доступа в интернет; только переход к записи звонка открывает внешний ресурс.
Для другого набора: `python annotation/server.py --dataset data/raw/control.json`.
Сохраняйте диалоги в формате полного успешного ответа API с `data.records`.

## Как размечать

1. Укажите своё имя и нажмите «Открыть разметку автора». Сначала задайте имя, затем начинайте работу.
2. Выберите диалог и прочитайте его целиком, включая сообщения бота и системные события.
3. Выберите критерий. Прочитайте его формулировку, правило выполнения, нарушения и N/A.
4. Выберите ответ: выполнено / нарушено, балл из заданной шкалы, N/A или «не уверен».
5. Напишите короткое проверяемое объяснение. Не подменяйте конкретный критерий общим впечатлением.
6. Отметьте галочками реплики-доказательства в транскрипте. Сохраняется точная цитата, роль и время из исходных данных. Не перепечатывайте цитату вручную.
7. Если действие отсутствует, укажите начало и конец проверенного участка. Например, для пропущенного представления — начало участия оператора; для отсутствия прощания — завершение обслуживания. Весь диалог выбирайте, только если проверили его целиком.
8. Для N/A укажите, какое условие неприменимости сработало, и подтвердите его репликой либо участком. N/A не означает «я не знаю».
9. Укажите уверенность человека. Низкая уверенность — повод отправить случай на разбор, а не автоматически уменьшить балл оператору.
10. Сохраняйте черновики. Ctrl+S сохраняет черновик. «Завершить диалог» проверяет заполненность всех критериев; спорные ответы допустимы, но не становятся эталоном.

Нельзя засчитывать приветствие бота как действие оператора. Положительный ответ требует
конкретной реплики оператора; для подтверждения идентификации допускается системное сообщение.
Для нарушения может быть достаточно проверенного диапазона,
если нарушение состоит в пропущенном действии.

Дикцию и интонацию по тексту не размечать. Если официальный критерий требует звук,
откройте запись и прослушайте её. При недоступном звуке выберите «не уверен», если правило
организаторов не предписывает иное. Абсолютные timestamps звонков не являются готовыми
смещениями плеера; инструмент открывает запись отдельно и не обещает переход к секунде.

## Какие критерии использовать

По умолчанию используется `checklist.official.json`, перенесённый из
`CQA_Chat_Quality_Checklist 1.pdf` (3 страницы).

| ID | Критерий | Ответ | Вес |
| --- | --- | --- | ---: |
| contact | Установление контакта | Да / Нет | 10 |
| needs | Выявление потребности | Да / Нет / N/A | 15 |
| identification | Идентификация | Да / Нет / N/A | 20 |
| consultation | Корректная и полная консультация | 0, 5, 10, 15, 20 / N/A | 20 |
| empathy | Эмпатия и клиентоориентированность | Да / Нет | 15 |
| management | Управление диалогом, скорость и грамотность | 0, 4, 7, 10 | 15 |
| closing | Завершение | Да / Нет / N/A | 5 |
| critical_errors | Грубые ошибки | Да — нарушение выявлено / Нет — не выявлено | без баллов |

Важные отличия от первоначального учебного примера:

- Контакт: приветствие на языке клиента и представление в первом ответе; N/A не разрешён.
- Завершение: (итог ИЛИ предложение дальнейшей помощи) И прощание; одного прощания недостаточно.
- Консультация и ясность общения оцениваются отдельно: неполный, но понятный ответ не означает автоматически низкую оценку за ведение.
- Грубые ошибки — три определённых основания и отдельный флаг. Автоматического обнуления итогового балла PDF не задаёт.
- Порог первой реакции 3 минуты, теги и вложения не оцениваются.
- Чатовый файл применяется к чатам. Для звонков используйте отдельную адаптацию `checklist.voice.json`, созданную после уточнения организаторов.

Уточнение организаторов для звонков теперь получено: логика восьми критериев аналогична,
письменная коммуникация адаптируется к устной. Используйте отдельный профиль
`checklist.voice.json`, а не применяйте неизменённый чатовый файл к звонкам.

Формула: `итог = 100 × сумма(вес × нормированная оценка) / сумма применимых весов`.
Для Да/Нет нормированная оценка 1/0; для шкалы — балл / максимум шкалы.
N/A исключается из числителя и знаменателя, итог округляется один раз до двух знаков.
При всех N/A итог отсутствует; при незаполненном или спорном взвешенном ответе — тоже.
Для округления используется Decimal и арифметическое ROUND_HALF_UP.

`checklist.example.json` оставлен для упражнений и не является официальной версией.
Если ранее был загружен другой чек-лист, загрузите официальный через интерфейс.
Для новой конфигурации используйте такой формат:

```json
{
  "name": "Чек-лист организаторов",
  "version": "official-1",
  "status": "official",
  "source": "Название и версия выданного PDF, страницы с критериями",
  "criteria": [
    {
      "id": "stable_criterion_id",
      "name": "Точная формулировка",
      "type": "binary",
      "weight": 10,
      "description": "Что проверяем, в каких репликах и в каких условиях",
      "pass_rule": "Однозначное условие выполнения",
      "fail_rule": "Однозначное условие нарушения",
      "na_allowed": true,
      "na_rule": "Условие, при котором критерий неприменим"
    }
  ]
}
```

Для шкального критерия используйте `"type": "ordinal"` и `"allowed_scores": [0, 1, 2]`
с реальными значениями официальной шкалы. В `description` распишите якорь каждого значения.
Если N/A запрещён, укажите `"na_allowed": false`.
Для подсчёта задайте `weight` всем критериям с баллами. Грубая ошибка имеет `is_critical: true`,
`type: binary`, `weight: 0`; ответ `pass` здесь означает «Да, нарушение выявлено»,
а `fail` — «Нет, не выявлено». `yes_label` и `no_label` задают понятные подписи в интерфейсе.
Поле `positive_evidence_roles` разрешает подтверждение нужной ролью (operator и/или system).
Не придумывайте финансовые регламенты, гарантии доходности или сроки, которых нет в исходных правилах.

После загрузки нового JSON создаётся новая область разметки по хешу всего чек-листа.
Поля `status: official` и `source` заполняет человек: программа не может проверить подлинность PDF.
Изменение текста, версии, шкалы или дополнительных полей меняет хеш. Сначала согласуйте чек-лист,
затем размечайте большой объём. Чтобы открыть старую область, загрузите ровно прежний JSON.

## Два разметчика и проверка

Сначала два человека независимо размечают одни и те же 5–8 диалогов под разными именами.
Включите RU, KZ, EN; звонки добавляйте после согласования применимости чек-листа.
Не смотрите на оценки другого до завершения своей работы.
Сравните расхождения по каждому критерию и выпишите причины: неоднозначное правило, N/A,
пропущенная реплика, недостаток знания языка или предметной области. Уточните инструкцию,
при изменении чек-листа повторите пилот на новой версии.

Затем второй человек открывает имя автора, проверяет ответы и доказательства, разрешает спорные
случаи и при необходимости меняет ответы. Он вписывает своё имя в «Проверяющий», ставит галочку
и нажимает «Завершить диалог». При изменении ответа галочка проверки снимается.
Все предыдущие сохранения остаются в `history/`.
Имена — метаданные для локальной работы, не подтверждённые учётные записи.

Если размечаете в одиночку, сохраните разметку без отметки второго проверяющего.
Её можно использовать для исследования, но не выдавать за независимо проверенный эталон.

## Хранение и экспорт

Автосохранения ответов нет. Сохраняйте кнопкой или Ctrl+S.
Сервер хранит файлы в `data/annotations/<хеш чек-листа>/<хеш автора>/<хеш диалога>.json`.
Имена файлов хешированы; исходный ID и автор лежат внутри файла.
Повторное сохранение увеличивает ревизию, прошлое состояние сохраняется в `history/`.
Конфликт двух открытых вкладок блокирует перезапись; обновите страницу и загрузите актуальную версию.
Изменение исходного транскрипта делает прежние ответы устаревшими. Интерфейс предлагает разметить
новый текст с чистого листа, предыдущая сохранённая версия сохраняется в истории при записи новой.

«Экспорт JSON» скачивает все текущие ответы всех авторов для выбранной версии чек-листа,
включая черновики, исходные диалоги и `eligible_for_reference` у каждой записи.
Флаг true означает: официальный по отметке человека чек-лист для нужного канала, актуальный текст,
завершённая человеческая разметка либо версия ИИ с подтверждением каждого критерия человеком,
нет «не уверен», заполнены сведения проверяющего. Это технический фильтр,
а не гарантия качества или согласия всех разметчиков.
Если один диалог размечен несколькими авторами, перед оценкой/обучением выберите одну
согласованную финальную запись. Не считайте их независимыми диалогами.

Разметка и исходные данные исключены из Git. Сохраняйте экспорты в `data/exports/`
или вне публичного репозитория: они содержат тексты реальных звонков.
Не закрывайте терминал сервера, пока браузер сохраняет ответ.

## Предварительная разметка всего DEV

Все 60 синтетических чатов прочитаны и предварительно размечены ИИ по восьми официальным критериям:
30 RU, 15 KZ, 15 EN, всего 480 решений. Это отдельный автор
`AI-разметка DEV v1 (проверить)`, которого можно выбрать в подсказке поля имени.
Эта партия содержит только чаты. Пять реальных звонков размечены отдельной голосовой партией; аудио не оценивалось.

Это описание первой чатовой партии. После уточнения организаторов пять звонков размечены
отдельно; актуальная совокупная партия всех 65 диалогов описана ниже.

Файлы в `data/exports/`:

- `ai-dev-preannotations.json`: разметка с транскриптами, точными цитатами, версиями и отчётом.
- `ai-dev-preannotations.jsonl`: одна аннотация на строку, без повторной упаковки всех транскриптов.
- `ai-dev-review-queue.json`: приоритетная очередь — грубые флаги, uncertain и medium/low.
- `ai-dev-report.json`: машинная сводка покрытия и исключений.
- `ai-dev-summary.md`: читаемая сводка и предварительные результаты каждого диалога.

В первоначальной версии 20 решений были uncertain, 52 направлены на приоритетную проверку;
после подтверждения пользователем определённых ответов в чатовой очереди остались 20 uncertain.
Актуальные счётчики видны в интерфейсе и отчёте, итог первоначально вычислен для 41 диалога.
Эти цифры описывают предварительную версию, а не качество модели. Уверенность разметчика не является
вероятностью правильности. Проверьте также выборку high-ответов, отдельно KZ и интерпретации завершения.
Фактические правила продукта требуют внутреннего источника. В массовой версии, например,
спорное завершение `p1-ru-003` оставлено uncertain; прежний учебный пример другого автора сохранён отдельно.

Решения хранятся в `data/annotations/ai-dev-v1.decisions.json`, исходные хеши — в
`data/annotations/ai-dev-v1.source.json`. Их импортирует `python annotation/import_preannotations.py`.
Скрипт не вызывает модель и не размечает новый текст эвристиками: он проверяет и сохраняет уже
подготовленные решения. Перед записью валидирует всю партию, проверяет покрытие и исходные хеши.
Повторный запуск сохраняет существующие правки под тем же автором, не перезаписывая их.
Пересоберите исходные решения из parts только при осознанном пересмотре; импорт существующих записей не обновляет.

У записей `origin: ai_preannotation`, `reviewed: false`, `eligible_for_reference: false`.
Их можно использовать для создания интерфейса, хранения, апелляций и предварительного сравнения с моделью.
Человеческое подтверждение можно сохранять в этой же версии, отдельно от происхождения ИИ;
для независимой разметки без подсказок используйте отдельное имя.
Для обучения не считайте весь набор автоматически проверенным. Все диалоги уже просмотрены ИИ,
поэтому исходный независимый test здесь не сохранён; организаторский контрольный набор остаётся отдельным.

## Голосовая адаптация и полная партия из 65 диалогов

В поле «Чек-лист» можно переключаться между чатовым и голосовым профилем.
Наборы аннотаций разделены по хешам: переключение не меняет и не удаляет чатовые оценки.
При загрузке своего JSON остаётся доступен пользовательский профиль.
Выбор профиля общий для локального сервера; сохранение со старым хешем в другой вкладке блокируется.

`checklist.voice.json` — адаптация команды на основании разрешения и уточнения организаторов,
а не отдельно изданный ими PDF. Вес и ступени оставлены от исходного чек-листа.
Генератор адаптации: `python annotation/build_voice_checklist.py`; он не изменяет чатовый JSON.

Критерий 4 оценивает полноту, корректность и необходимые действия. Для проверки продуктовых фактов
используйте материалы Freedom Broker. Отсутствие эталонных ответов на каждый контрольный разговор
не мешает сопоставлять консультацию с документированными правилами; но без этих материалов
нельзя выдавать предположение за проверенную корректность.

Критерий 6 для устной речи оценивает логику разговора, понятность, уместность и корректность формулировок,
управление ожиданием/удержанием. Темп, дикция, акустическая разборчивость и интонация оцениваются
только после прослушивания. Ошибки ASR не являются доказательством плохой речи оператора,
а разрывы между timestamps не доказывают неуместную тишину.
При удержании внутренние консультации коллег не считаются автоматически слышимыми клиенту.

Все 5 звонков прочитаны и предварительно размечены по транскриптам: 40 решений,
из них 16 uncertain. Аудио не скачивалось и не прослушивалось. Ни у одного звонка полный балл
не рассчитан из-за неопределённых взвешенных критериев — их не заменяли нулями или N/A.
Автор: `AI-разметка звонков v1 (только транскрипт)`.
Факт использования источников сохранён в `assessment_context`: basis, audio_reviewed,
акустические наблюдения not_assessed, ограничения и исключённые внутренние диапазоны.
Сервер не принимает акустические выводы при audio_reviewed=false и не разрешает выдавать
исключённые внутренние реплики за доказательства общения с клиентом.
В интерфейсе эти сведения показываются как описание основания оценки; для оценки после прослушивания
требуется сохранить соответствующий assessment_context (например, через API), а не просто открыть ссылку на аудио.

Импорт: `python annotation/import_voice_preannotations.py`.
Решения лежат в `data/annotations/ai-voice-v1.decisions.json`; исходные хеши сохраняются отдельно.
Импорт проверяет всю партию до записи и не перезаписывает существующие правки.

Актуальные файлы:

- `data/exports/ai-voice-preannotations.json` — 5 звонков с отдельной версией чек-листа.
- `data/exports/ai-voice-review-queue.json` — приоритетная проверка звонков.
- `data/exports/ai-voice-summary.md` — ограничения и порядок проверки.
- `data/exports/ai-dev-all-preannotations.json` — все 65 диалогов и 520 решений, словарь двух чек-листов.
- `data/exports/ai-dev-all-review-queue.json` — общая очередь проверки по актуальным записям.
- `data/exports/ai-dev-all-report.json` — общая машинная сводка.

У каждой аннотации в общей партии есть свой checklist_hash. Не пересчитывайте голосовые ответы
по чатовой версии автоматически и не сводите разные версии чек-листа к одному фиксированному набору меток.
Это предварительная разметка ИИ; человеческая проверка и независимая оценочная выборка по-прежнему нужны.

## Продолжить ту же версию с неуверенных оценок

Пользователь сообщил, что существующую разметку уже просмотрели и подтвердили.
Это подтверждение учтено для определённых ответов, без изменения их баллов, объяснений и доказательств.
На момент подтверждения принято 484 из 520 решений; осталось 36 «не уверен».
Отдельная копия под новым автором не создаётся. Прежний origin=ai_preannotation сохраняет происхождение,
а human_verification и human_checked фиксируют человеческое подтверждение отдельно.
Независимая проверка вторым человеком этим автоматически не заявляется.

Откройте http://127.0.0.1:8765/?review=1 или нажмите «Продолжить разметку».
Инструмент сам выбирает версию чек-листа, диалог, автора и нужный критерий.

1. Прочитайте правило, текущий ответ и исходное объяснение ИИ в раскрывающемся блоке.
2. Если исходных материалов достаточно, выберите окончательный ответ, обновите объяснение и доказательства.
3. Нажмите «Подтвердить и дальше»: сохраняется эта же версия, прогресс записывается на диск.
4. Если нужны документы или аудио, используйте «Отложить». Отложенное остаётся неподтверждённым;
   повторный запуск очереди возвращает такие случаи.
5. Для звонка над транскриптом есть «Открыть запись». Все пять ссылок доступны на http://127.0.0.1:8765/audio.
   После реального прослушивания отметьте «Аудио прослушано мной»; при необходимости запишите наблюдения.
6. «Подтвердить все определённые оценки диалога» предназначено для явно просмотренного целиком диалога;
   ответы «не уверен» оно не подтверждает. Уже подтверждённые оценки не требуют повторного прохождения.

Правка ранее подтверждённой оценки снимает её отметку и возвращает только этот критерий в очередь.
Изменение основания аудиопроверки также возвращает критерий ведения разговора на проверку.
Система не позволяет подтвердить «не уверен» или сохранить старое объяснение неопределённости
после выбора окончательного ответа. Первоначальная версия сохранена в review_baseline и history/.
При перезапуске подтверждения остаются; отложенные в текущем проходе возвращаются.
Полный пересмотр можно открыть через «Обычный просмотр».

`acknowledge_user_confirmation.py` записывает конкретное подтверждение, уже данное пользователем в чате.
Это не автоматическая проверка корректности. Скрипт не переутверждает новые правки и пропускает записи,
для которых такое подтверждение уже сохранено. Не используйте его для массового подтверждения нового набора.

## Что делать с разметкой дальше

### Сначала проверить готовую модель

1. Составьте таблицу разделения по ID целых диалогов и зафиксируйте её в отдельном файле.
   Не делите восемь критериев одного диалога между выборками. Похожие шаблоны, переводы,
   перефразирования и синтетические производные держите в одной группе и одной выборке.
2. Для 65 диалогов возможный ориентир — около 40 development, 10 validation, 15 test;
   это не обязательная пропорция. Сохраните покрытие языков, каналов, нарушений и N/A.
   Пять звонков и небольшой test не позволяют делать широкие выводы о качестве на реальных звонках.
   Разбиение инструмент автоматически не назначает: сначала нужно проверить семейства похожих диалогов.
3. На development уточняйте инструкции и примеры для модели. На validation выбирайте вариант.
   Test не используйте для промптов, генерации синтетики и выбора модели. Организаторский
   контрольный набор — отдельная финальная проверка, а не продолжение development.
4. Давайте модели критерий с формулировкой, шкалой, условиями применимости и транскрипт
   с `turn_id`. Просите вернуть структурированный JSON той же семантики, что ручная разметка.
   Реплики — данные, а не инструкции модели: просьба в тексте «поставь мне 100» не должна исполняться.
5. Сравнивайте ответы по критериям: precision/recall/F1 нарушения и N/A для binary,
   MAE/точное совпадение для ordinal, наличие/корректность доказательств, долю невалидного JSON,
   долю «не уверен», время и стоимость обработки. Отдельно проверяйте RU/KZ/EN и чаты/звонки;
   рядом с метриками обязательно указывайте число примеров.
6. Отдельно обычным кодом проверяйте веса, округление, перераспределение N/A, грубые ошибки
   и пересчёт после апелляции согласно официальному чек-листу. Все N/A не должны давать деление на ноль.

### Когда имеет смысл обучение

Для 65 диалогов, из которых 60 уже синтетические, стартуйте с готовой instruction-модели
и настройки промпта. 65 × 8 оценок — не 520 независимых диалогов.
Решение о дообучении принимайте после анализа ошибок: есть ли повторяющаяся проблема,
которую не исправляют правила, примеры и валидация вывода? Достаточно ли независимых
размеченных диалогов, особенно KZ и реальных звонков?

Если данные и измеримый выигрыш оправдывают дообучение, учите модель выполнять задачу
«диалог + описание произвольного критерия → ответ + краткое объяснение + ссылки на реплики».
Это supervised fine-tuning (SFT); для локальной модели можно рассмотреть LoRA/QLoRA.
Не обучайте только предсказывать восемь фиксированных ID: организаторы меняют критерий.
Не обучайте арифметику итогового балла и ASR — баллы считает код, транскрипты уже выданы.
Сначала проверьте точность языковой модели на KZ на ваших данных, а не по её заявлению о поддержке языка.

Одна потенциальная обучающая пара (после выбора только train-диалогов):

```json
{
  "prompt": [{"role": "user", "content": "Критерий с правилами и шкалой + транскрипт с turn_id"}],
  "completion": [{"role": "assistant", "content": "{\"verdict\":\"fail\",\"score\":null,\"reason\":\"Краткое проверенное объяснение\",\"evidence_turn_ids\":[],\"checked_span\":{\"start_turn_id\":\"t0001\",\"end_turn_id\":\"t0005\"}}"}]
}
```

Это схема будущей подготовки данных, не готовый обучающий датасет и не команда обучения.
Не включайте test в обучающие пары. Используйте одну согласованную запись на диалог.
Проверяйте, что JSON цели валиден, ссылки существуют и ответ согласован с критерием.

### Синтетика

Добавляйте адресные пары только после анализа ошибок: удаление обязательной реплики,
действие выполнил бот вместо оператора, условие N/A, переключение языка, обрезанный разговор.
Результат каждой генерации проверяет человек; после изменения текста прежние ссылки-доказательства
могут стать неверными. Производные train-диалога остаются в train. Из test ничего не генерируйте.
Автооценка той же моделью, которую вы проверяете, не заменяет человеческий эталон.
